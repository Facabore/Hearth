# ADR 0004 — Web UI tests and performance gates

- Status: Accepted (2026-10-20); amended 2026-10-28 by the SPA cut-over ([ADR 0006](0006-client-first-single-page-app.md), #199) and by the owner's cold-load budgets (below)
- Stories: HU-E9-01, HU-E9-02, HU-E9-03, HU-E9-13 (rulings P132, P134)

## Context

The owner kept React and Next.js on one condition: the UI must be fast, with Core Web Vitals budgets that fail CI. The stories are written in Gherkin and the UI Definition of Done asks for accessibility in light and dark themes.

## Decision

- Components and containers run in a Vitest `ui` project on jsdom 30.1.2 with Testing Library and axe-core 4.13.0, contrast off (P132). jsdom over happy-dom: axe-core's ARIA and name computations are validated on jsdom, and Testing Library is mature on it.
- `@e2e` scenarios run with Playwright 1.63.0 and playwright-bdd 9.2.1 against the single-page app's build and a disposable PostgreSQL. Since the cut-over (#199) every spec opens the SPA through Vite's preview, which serves the build at the root and proxies `/api/*` to the standalone API server as Caddy does in production; `@axe-core/playwright` 4.13.0 scans every screen in light and dark in real Chromium, contrast included.
- Lighthouse 13.5.0's Node API measures each route of the SPA five times with its mobile defaults and fails on the medians above LCP 2500 ms, CLS 0.1, TBT 200 ms or the route's script budget in `tests/performance/budgets.json`; a route without a budget fails (P134). `@lhci/cli` was not adopted: it has no hook for authenticated routes and a heavier dependency tree.
- The e2e server, its database container's label and every spec read `E2E_PORT` (default 3100), so two worktrees can run e2e at once, each against its own build; the teardown removes only its own port's containers, and a server already on the port is reused only with `E2E_REUSE=1` (#140).
- Screens that leave the happy path are tested where they can be reached. The SPA's not-found screen (an address that matches no route, a space or record the API does not find) is scanned by axe in light and dark and measured by `layout.spec.ts`, and so are Settings and New space inside a shared space and the home and Saldos links to the members. The SPA answers every app address with its shell, so an unknown address gets that screen with a 200 status; ruling N1's 404 status applies to the API and to unknown files, and the web image's smoke test in CI pins the latter. The error screens (an error boundary, the sign-in outage) need a failing API that the e2e server cannot produce, so Vitest and axe-core in jsdom cover them (N2).
- INP is measured with `web-vitals` 6.2.3 over the record flow on a 4× slower CPU, because a Lighthouse navigation run has no interaction to measure.
- The budgets are enforced on the SPA's build as production serves it: Lighthouse loads it from a Caddy container (`caddy:2.11.7-alpine`, `tests/performance/Caddyfile.perf`) over HTTPS and HTTP/2, with Caddy's local CA and the web image's handlers, compressed as Caddy compresses it; the e2e specs keep Vite's preview. `pnpm spa:budget` also holds each route's chunks to `tests/performance/spa-budgets.json` on every run (ADR 0006). Two code choices keep a route from paying for screens it does not show: `package.json` declares `sideEffects: ["**/*.css"]` (a route's client bundle then holds only the modules it uses, not every client component a barrel file re-exports), and `Sheet` imports its Radix Dialog panel on first open.
- Two more cuts took about 18 KiB of script off every route (#141): the message catalogs are compiled at build time (next-intl's `precompile` then; since #199 `icu-minify` in `vite.spa.config.ts`), so the client ships its small formatter and not the ICU parser (about 9 KiB), and `cn` joins classes with `clsx` alone, without tailwind-merge (about 9 KiB). Because nothing resolves conflicting Tailwind utilities any more, a component never overrides a class it also sets: `Button` has a size for each box it takes (`compact`, `chip`, `lgFlow`, `iconCompact`) and `TextField` has `large`, and `atoms.test.tsx` fails when a variant sets two radii, heights or text sizes. The budgets were then lowered to about 3 KiB above the new measurements.

## Consequences

- A missed budget is the owner's decision, never a silent raise. The first measurement set the script budgets just above the measured bundles, because the framework alone is 129 KiB gzip (ruling P154).
- Lighthouse's simulated throttling varies on shared runners; medians of five reduce the noise, they do not remove it. Simulated LCP is bimodal on this app (it steps in about 150 ms and swings by a second between runs), so a median of three failed about one CI run in twenty with no code change; five runs cut that to under one in fifty (M6b Task 21, amending P134). [ADR 0005](0005-measure-lcp-under-applied-throttling.md) times LCP under applied throttling instead (issue #182), because the swing moved the whole app between runs; CLS, TBT and script stay simulated.
- The `performance` job blocks the image build.
- Amended 2026-10-28: the `performance` job runs only on a push to `main` and on demand (`workflow_dispatch`), not on pull requests or on `development`. The owner's ruling: "siento nos estamos realentizando por despliegues y pruebas, dejemos eso para el final no puede ser 20m en cada Pr y estamos tirando PRs cada 2x3, al final validamos eso." A budget missed on `main` still blocks that release's images. The SPA's chunk budgets (ADR 0006) take seconds and stay on every run, in the `e2e` job.
- Amended 2026-10-28 by the owner ("Amend the budgets"), for the SPA's cold load (#199). With no server-rendered HTML, a screen paints only after its HTML, the app's script, the profile, the screen's chunk and its data arrive, each a round trip of about 0.6 s on Lighthouse's applied slow 4G; 2.5 s is not reachable client-side. The cut-over's first measurement also measured through Vite's preview over HTTP/1.1, where six connections per host queued the SPA's small chunks: 6.3 to 9.2 s, a cost no person pays behind production's HTTP/2. Since then:
  - The gate measures behind Caddy over HTTP/2 (above).
  - The HTML starts the profile and spaces reads and the likely catalog's download while the app's script downloads (`src/spa/early-html.ts`), and the write plans load after the first screen.
  - LCP is held to 6000 ms on a signed-in screen and 4000 ms on a visitor's (`visitorLcpMs`: sign-in, sign-up, an invitation, a claim), just above CI's measurement on 2026-10-28: 3.8 to 5.6 s signed in (the Plan tab's views are the slowest), 3.0 to 3.6 s for a visitor.
  - Each route's script budget is CI's measurement plus 3 KiB (P154), now 163 to 298 KiB: the whole app shell, the screen's chunks, the catalog and, within the trace, the write plans. Rulings P198 and P221 raised their caps where those budgets passed them (`budgets.test.mjs`, `routes.test.mjs`).
  - TBT (200 ms), CLS (0.1) and INP (200 ms) are unchanged; the SPA measured TBT 6 to 49 ms, CLS 0 and INP 32 to 64 ms.
  - A follow-up can still lower LCP: the screen's own chunks could start with the HTML too, which needs the route table in the HTML.
